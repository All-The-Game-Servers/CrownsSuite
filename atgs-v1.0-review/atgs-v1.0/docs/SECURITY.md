# ATGS Security Model

## Identity layers

ATGS has two kinds of identity:

1. **Machine identity** — Keepers, Relays, and Progenitor desktop installs authenticate via mTLS with certs signed by Central's internal CA. Every control-channel envelope is additionally signed with Ed25519 for replay protection.

2. **Human identity** — Admins log into the Progenitor admin console with email + password. Passwords are hashed with argon2id (RFC 9106 low-memory profile). Sessions are server-side tokens stored as HttpOnly Secure cookies with 24-hour sliding expiry.

## Private CA

Central runs its own internal CA. The root key is generated by `central bootstrap-ca` and lives in the `ATGS_CENTRAL_CA_DIR` directory. The CA signs:

- Keeper client certs (on enrollment, 1-year validity)
- Relay client certs (via `central mint-relay-cert`)
- Progenitor client certs (via `central mint-progenitor-cert`)
- The Central server cert itself (dev mode only; production should use a real cert from Let's Encrypt or similar on the admin-facing port)

The CA private key is critical. Protect the directory with `0700` permissions and back it up securely. Loss of the CA key means re-issuing every cert.

## Envelope signing (Phase 7)

Every message sent on the keeper-central control channel carries an Ed25519 signature. Central signs with its own key (also in `ATGS_CENTRAL_CA_DIR`), keepers sign with their own keys (generated at enrollment, stored in the keeper's state dir at `ed25519.key`). The signature protects against:

- Tampering (content cannot be altered without invalidating the signature)
- Replay (nonce + timestamp must be fresh; the verifier has a per-keeper replay cache)
- Forgery (an attacker who steals the mTLS cert still can't forge messages without the Ed25519 key)

Enforce strictly with `ATGS_CENTRAL_REQUIRE_SIGNED_TASKS=true`. During a rollout (existing keepers without Ed25519 keys), leave it `false` until all keepers have re-enrolled.

## Revocation

Two paths that work together:

1. **Active revoke task**: Central sends `keeper.revoke` over the control channel; the keeper wipes its state and exits. Works when the keeper is online.

2. **CRL at TLS handshake**: Central maintains an on-disk certificate revocation list at `<CADir>/revocations.txt`. At every mTLS handshake, the keeper's cert serial is checked against the CRL and rejected if listed. Works when the keeper reconnects later with stale credentials.

Trigger both via `POST /api/v1/keepers/{id}/revoke` with `{"reason": "..."}`. Both fire atomically.

## Password policy

- Minimum 12 characters (enforced at the password-set endpoints)
- Stored as argon2id PHC-format strings: `$argon2id$v=19$m=65536,t=2,p=4$<salt>$<hash>`
- Verification is constant-time via `subtle.ConstantTimeCompare`
- Timing-equalized: unknown-email login attempts run a dummy verify so wrong-email and wrong-password look identical to an attacker

## Rate limits

Per-keeper token bucket on the Central dispatcher: 100 tasks/minute, burst 500. Configurable via `ATGS_CENTRAL_TASK_RATE_PER_MIN` and `ATGS_CENTRAL_TASK_RATE_BURST`. Returns `ErrRateLimited` upstream to the admin API, which translates to HTTP 429.

## Audit trail

Every admin action is written to the `audit_log` table:
- User logins (success and failure)
- Enrollment token mints and consumption
- Keeper revocations
- User create/disable
- Instance create/start/stop/delete
- Backup create/restore
- CRL additions

Optional streaming to syslog/file via `ATGS_CENTRAL_AUDIT_SYSLOG_PATH`. Format is newline-delimited JSON.

## What to rotate, and when

| Secret | Lifetime | Rotation trigger |
|---|---|---|
| CA private key | Indefinite | Compromise only; re-issue all certs |
| Central Ed25519 signing key | Indefinite | Compromise; re-enroll all keepers |
| Keeper mTLS cert | 1 year | Auto-renew near expiry (future); revoke on compromise |
| Keeper Ed25519 key | 1 year | Auto with cert rotation |
| Admin password | Per-policy | Compromise, leave, policy |
| Enrollment tokens | 15 minutes | N/A — one-shot |
| Session cookies | 24 hours sliding | N/A — auto-rotates on use |

## Threat model: what ATGS defends against

- **Stolen mTLS cert**: attacker must also have the Ed25519 key to forge messages
- **Stolen Ed25519 key + cert**: attacker can forge messages but is rate-limited; audit log reveals the behavior; admin revokes
- **Replayed messages**: rejected by nonce cache and timestamp skew window
- **Tampered messages**: rejected by Ed25519 signature verification
- **Database dump leak**: passwords are argon2id-hashed; session tokens are sha256-hashed (only the hash is stored, not the token)
- **User enumeration via login**: timing equalized with dummy argon2id verify on unknown-email

## What ATGS does NOT defend against (yet)

- DDoS at the TCP/UDP level — use a cloud LB or DDoS mitigation service
- Insider threats with CA access — protect `ATGS_CENTRAL_CA_DIR` with filesystem ACLs and audit
- Compromised keeper host executing tasks maliciously — keepers are trusted to do what Central tells them; a rooted keeper could lie about instance state
- Brute force against the admin login beyond what rate limiting provides — consider fail2ban or similar on the admin listener in production
